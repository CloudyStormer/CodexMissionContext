# 侧边栏布局候选与并发冲突

每次发布新布局都先在本目录保存候选；候选只包含共享逻辑 ID、顺序、置顶状态、规范化摘要和版本元数据，不保存 Codex 原始状态、数据库、session 或明确排除对象。共同项目内的临时任务属于同步范围，必须进入任务顺序。候选既是两阶段发布的第一阶段，也是以后重建设备基线的不可变快照。

发布包含任务清单版本 `5` 全部 39 项任务的下一候选时，先读取 `同步清单/完全对齐交接包.md` 的目标顺序与规范化摘要，并取得同一运行 ID 的 A、B 完整任务快照和唯一合并任务包；交接包本身不是候选，也不能绕过两阶段晋升。双端顺序回执只能在候选晋升为有效布局并实际应用后生成，不能作为候选发布前提。

## 何时创建候选

- 任何设备准备发布新的共享布局版本。
- A、B 从同一前序布局版本产生不同的下一版本。
- 当前设备准备应用远端新版本前，发现本地可见共享布局已经偏离本设备上次确认的非零完整或部分应用基线。
- 任务清单从旧的部分任务基线迁移到完整任务并集，并已取得同一运行 ID 的 A/B 完整快照、唯一合并任务包和交接包目标摘要。

基线为版本 `0` 表示尚无受管布局，首次对齐直接采用远端有效版本；用户明确要求保留本机当前布局时除外。

## 文件名

使用：

```text
<前序版本>-<设备ID>-<UTC时间>-<候选ID>.md
```

设备 ID 只能是 `A` 或 `B`；UTC 时间使用 `YYYYMMDDTHHMMSSZ`；候选 ID 使用短随机或提交标识，避免两端同名。


摘要计算必须对“规范化清单”四行及每行结尾换行的 UTF-8 字节执行 SHA-256。候选晋升后不得改写这四行、摘要、来源设备或前序版本；只允许追加选择结果、规范版本和提交信息。

触发原因为“完整任务并集迁移”时，六个候选来源字段必须全部填写并可校验，均不得写 `NOT_APPLICABLE`：运行 ID 必须对应 `同步运行/` 下唯一目录，两份快照和唯一合并任务包的文件 SHA 必须匹配，目标修订与目标顺序 SHA 必须匹配该轮读取的 `完全对齐交接包.md`。合并包中当前全部逻辑任务必须恰好各出现一次且 `merge_state` 全为 `READY`；READY 记录内单端的 `source_body_sha256_a/b: MISSING` 表示待补镜像，是允许的正常输入。其他触发原因的六个候选来源字段统一写字面量 `NOT_APPLICABLE`，不得留空。候选来源字段缺失、文件哈希失败、任务缺项/重复或任一 `merge_state` 非 `READY` 时禁止发布或晋升候选。

## 处理规则

1. 第一阶段只提交并推送候选，不修改 `同步清单/侧边栏布局.md`。
2. 再次 fetch；只有远端规范仍是候选的前序版本，且同一前序版本只有一个待晋升候选时，第二阶段才在新提交中把它提升为“有效”的唯一下一版本。
3. 晋升前已有多个同基线候选时，规范布局保持前序版本。两端候选使用不同文件正常 Git 合并，不能按时间戳擅自选胜者；用户选择或明确合并后才晋升。
4. 有效版本晋升后才收到基于其前序版本的迟到候选时，不重写历史、不回滚已经应用的设备；把当前规范布局标为“冲突待裁决”，未应用设备暂停，用户裁决后把结果发布为再下一版本。
5. 发布后在候选文件追加选择结果和规范布局版本；保留候选作为基线快照和冲突审计记录，不删除历史。
