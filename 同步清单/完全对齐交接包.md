## 任务内容必须怎样一致

“内容一致”不是复制原始聊天，而是 A、B 同一逻辑任务收到完全相同的一版精简语义正文。正文固定使用以下八节：

1. `当前目标`
2. `已完成`
3. `关键决定与原因`
4. `文件与命令`
5. `验证`
6. `失败与风险`
7. `下一步`
8. `原设备与更新时间`

哈希只覆盖上述八节正文，不包含消息头、模板元数据或回执。规范化口径固定为：UTF-8 无 BOM、Unicode NFC、LF 换行、移除每行行尾空白、文件末尾恰好一个换行。`原设备与更新时间` 使用语义来源的真实时间；重复投递不得改成投递时间，否则无新语义时 SHA 无法保持稳定。对规范化正文计算 SHA-256。发送到任务的消息头固定为：

```text
[SYNC-CONTEXT v1]
run_id=<运行ID>
logical_task_id=<逻辑任务ID>
body_sha256=<正文SHA-256>
```

A、B 回执中的 `body_sha256` 必须相同。发送请求成功不等于内容已一致；必须用正式任务读取能力回读任务中的 `[SYNC-CONTEXT v1]` 正文，按相同规则重新规范化并计算 SHA。无法回读精确正文时记为“未验证”。正文存在实质冲突时，合并包同时保留冲突事实并把任务标为阻塞，不按时间戳盲目覆盖。没有新语义且摘要 SHA 未变化时不重复堆叠全文；只有为了验证非置顶最近更新顺序时，才发送引用同一 SHA 的短检查点。

## 实体、内容和顺序的执行方法

1. 按项目和任务并集只增不减：补齐缺失项目后，必须回读真实 `projectId`；补齐缺失任务后，必须回读真实 `threadId`、标题和项目归属。缺少标题设置/验证或精确任务正文读取能力时，对应分量是硬阻塞，不能只凭创建或发送成功报完成。
2. 同一逻辑任务在 A、B 可以有不同本地 ID，但标题、逻辑项目和语义 SHA 必须一致。
3. 先取得 A/B 完整任务快照和唯一合并包，再按 `侧边栏布局候选/README.md` 的“完整任务并集迁移”分支发布候选；候选四行规范化内容及 SHA 必须与本文件完全相同，并保留版本 `2` 已有任务的相对顺序。候选两阶段晋升为新的“有效”布局之前，只补实体和语义，不按本文件的候选任务顺序重排。
4. 新有效布局确认当前 39 个目标任务全部非置顶后，才使用正式置顶接口逐项核对并取消同步范围任务的置顶。明确排除任务的置顶状态不动。
5. 新有效布局发布后，若正式任务列表明确保证非置顶任务按最近更新时间返回，可在没有任意排序接口时尝试“最近更新规范化”：仅发送引用同一语义 SHA 的短检查点，按有效布局目标顺序从下到上串行处理，每项等待完成后再处理上一项；期间不得并发更新其他共享任务。完成后必须重新读取正式列表，只有共享子序列逐项完全匹配才算成功。调用任务自身或并发完成会破坏顺序时，不使用或不声称该方法成功。
6. 多个置顶任务的内部顺序、项目置顶和项目任意顺序没有正式排序能力时，不猜测接口副作用，也不写 Codex 原始状态；记录硬阻塞并等待正式 API 或用户可见界面能力。
7. 排序授权不包括删除、归档、重命名或隐藏任何对象。
