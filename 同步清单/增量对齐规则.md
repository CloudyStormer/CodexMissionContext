# 项目并集和任务列表增量对齐规则

## 目标

让 A、B 两台设备包含相同且最完整的可同步项目集合，同时绝不通过删除现有内容获得表面一致。

项目公共范围定义为：

> A 的可同步项目列表 ∪ B 的可同步项目列表

任一设备出现新项目，除明确排除项外，都要登记为并集项目，补充真实 Git 来源，并在另一台设备补齐。同步范围任务同样采用 A、B 全量并集：共同项目中的每个可见任务都登记稳定逻辑 ID，在另一端对应项目建立可见镜像，并发送可直接续接的精简语义上下文。

## 发布本机项目清单

1. 拉取 `CodexMissionContext` 最新版本。
2. 使用 Codex 项目列表能力读取本机实际项目；能力不可用时标记“部分覆盖”，不得凭记忆声称完整。
3. 对每个可同步本地项目记录逻辑 ID、显示名称、真实根目录、本地 `projectId`、包含的全部 Git 仓库、remote 和默认分支。
4. 本机项目尚未出现在 `项目清单.md` 时，直接把它加入并集；不再长期保留为只报告的“额外项目”。
5. 将本机映射、并集清单版本、新增项目及其取得方式提交并推送，使另一台设备能够发现。
6. `AI学习`、`AI 教学助手`、`AI 笔记助手` 继续按最高优先级排除；账号级且没有本地 Git 路径的云项目只记录说明，不作为克隆目标。

没有 remote、权限或可传递来源的项目仍进入并集的待补齐状态，但不得创建空壳冒充完成。来源准备好后再由另一端实际克隆。

## “开始同步”的完整双向含义

用户发送四字口令“开始同步”时，以同一运行 ID 让 A、B 两端各由一个维护任务完成代码与对话两类交接：

1. 发起端先读取 `同步清单/完全对齐交接包.md`，再生成唯一运行 ID；另一设备维护任务可达时只发送一次执行请求，对端沿用同一 ID 且不反向派发。不可达时记录对端未参与，继续当前设备。
2. 两端分别遍历所有可见共同项目任务，不限当天或是否长期；以精准压缩方式保存用户要求、结论、原因、文件、命令、测试、阻塞和下一步。A、B 各自写入 `同步运行/<运行ID>/A-任务快照.md` 或 `B-任务快照.md`；发起端取得两份快照后按逻辑任务 ID 生成唯一 `合并任务包.md`。在缺失端对应已保存项目创建同名可见镜像，把合并包中的同一版规范化正文和 SHA-256 实际发送到两端任务。“所有任务”只授权补齐任务实体和交接语义，不授权擅自继续业务遗留需求。
   若扫描发现交接包目标之外的新同步范围任务，旧运行立即标为目标过期；先提升任务清单版本并更新交接包目标修订、顺序、数量和 SHA，推送后由两端用新运行 ID 重新生成快照。不得用旧 39 项目标发布布局候选或完成回执。
3. 两端分别在本机执行第一阶段：遍历全部共同项目 Git 仓库，先 fetch 并安全取得远端提交；脏工作树需要对齐远端时，使用可恢复的保护 stash，恢复冲突则保留 stash 和现场并阻塞该仓库。
4. 只有当前设备全部可达仓库完成远端取得阶段后，才进入本机第二阶段：审查、验证并提交安全的本地普通改动，再次 fetch、安全 rebase、push，并验证 `HEAD` 与 upstream 一致。
5. 已有未推送且可独立确认的提交必须在第二阶段上传。敏感内容、失败验证、业务歧义、冲突或不可达来源不得强行提交；准确记录后继续其他独立仓库。
6. 两端分别提交并推送 `CodexMissionContext` 的完整语义交接；结束前再次 fetch 并合并同一运行 ID 的两端报告。
7. A、B 分别写入本机回执，逐项记录项目/任务真实 ID、标题、归属、语义 SHA、共享索引、置顶和 Git 最终状态。只有两端回执均已取得、两端各自检查范围全部与 upstream 一致、项目与任务并集已补齐、每个任务的同一版精简交接已送达、共享顺序与置顶已验证，才可声称“两端全部同步”；否则只报告当前设备结果和双端剩余项。

## 侧边栏布局对齐

项目实体采用 A、B 并集；共享侧边栏布局采用 `同步清单/侧边栏布局.md` 中带版本的最新有效发布状态。`同步清单/完全对齐交接包.md` 保存当前确定性项目目标及完整任务目标；尚未按两阶段协议晋升的完整任务顺序只作为下一版本输入，不冒充有效布局。布局只包含逻辑 ID，不复制 Codex 原始本地状态；“已发布”与“已应用”分别记账。

用户发送四字口令“开始同步”时：

1. 先拉取布局状态和当前设备已应用版本。只有标记“有效”的规范布局可以自动应用。当前设备落后时，依据设备记录引用的不可变候选快照和 SHA-256 摘要重建本机上次确认的完整或部分应用基线，再与当前可见共享布局比较；已有非零基线且本地已偏离时，把本地状态保存为并发候选并停止自动应用。基线为 `0` 的首次对齐按远端有效版本执行，但用户明确要求保留本机当前布局时，先保存候选并停止；快照或摘要无法校验时也不得自动覆盖。
2. 对共同项目同步项目置顶顺序和非置顶顺序；对任务并集中的全部同步范围任务同步置顶状态和共享子序列。`AI学习`、`AI 教学助手`、`AI 笔记助手`、明确排除的个人任务和账号级云项目保持本机原样并从比较中排除。
3. 形成下一版本候选有三个并列条件：其一，当前设备已完整应用最新布局且用户当前可见的共享布局发生明确变化；其二，当前设备仍缺少并集对象，但其余可见共享对象已经按最新布局验证，缺失对象保持上一版本的置顶区域及其相对每个既有共享对象的前后关系，当前变化明确，且没有同基线并发冲突；其三，任务清单从旧的部分任务基线迁移到完整并集，且同一运行 ID 的 A/B 完整任务快照、唯一合并任务包和交接包目标摘要均已取得。第二种情况不得从部分视图移动缺失对象，发布设备仍按已部分应用记账；第三种情况覆盖完整任务并集，保留旧任务置顶区域和相对顺序，新任务按交接包确定性项目分组顺序插入，不要求尚未存在的新布局回执作为候选前提。首次由触发“开始同步”的设备形成版本 `1` 候选。
4. 源设备暂缺的既有并集项目必须保持上一版本的置顶/非置顶区域，并保持它与每个仍存在共享项目的相对前后关系；不能唯一保留时停止发布。普通分支中新项目或任务没有既有位置时追加到非置顶区末尾；完整任务并集迁移分支按交接包插入新任务，但不得改变旧任务的相对顺序。目标设备只收到新版本时记为待应用；实际尝试后缺少项目或任务才记为已部分应用。单纯应用远端版本时不回发残缺布局。
5. 使用稳定合并应用共享顺序：明确排除的项目和任务置顶状态保持不变，它们在各自置顶区和非置顶区内的相对顺序保持不变；只重排共享对象形成的子序列。工具只能整体重排而无法保证这一边界时，标记部分应用且不执行。
6. 应用必须通过正式 Codex API 或用户可见界面完成。只有最新有效布局已经包含完整任务顺序时，正式任务列表若明确保证非置顶任务按最近更新时间返回且目标任务全部非置顶，才可以用同一语义 SHA 的短检查点按有效布局顺序从下到上串行更新并逐项等待，再回读验证共享子序列；活动任务或并发更新时间使顺序不确定时不使用或不声称成功。候选晋升前不得按候选顺序重排。该方法不能用于多个置顶任务的内部顺序，也不能用于项目顺序。其他能力缺失时，只允许只读提取 `project-order`、`pinned-project-ids` 和 `pinned-thread-ids` 并转换为逻辑 ID；严禁提交或写回 Codex 原始状态、数据库、session 或缓存。
7. 每台设备分别记录 `设备状态确认来源与时间`、`已完整应用侧边栏布局版本`、`已部分应用侧边栏布局版本`、`本设备已确认待应用版本`、`已部分应用未完成逻辑 ID` 和 `本机上次确认布局基线`。只有目标设备实际拉取后才能由该设备写“已确认待应用”；发布端另记“待目标设备获取版本”和预期阻塞，不能替目标设备预报收件或应用结果。实际尝试并只完成一部分时才更新已部分应用；全部共享对象验证成功后才提升完整版本并清空其余状态。
8. 排序和置顶授权不包括删除、归档、重命名、隐藏项目或任务。新布局按 `同步清单/侧边栏布局候选/README.md` 两阶段发布：先单独推送候选，再 fetch；只有远端规范仍为前序版本且同基线候选唯一时，第二次提交才提升为有效下一版本。晋升前有竞争候选时规范保持前序版本；晋升后才出现迟到的同基线候选时，不回滚已应用设备，把当前规范标记“冲突待裁决”并暂停继续应用，等待用户选择或明确合并成再下一版本。

## 一次对齐流程

1. 拉取最新完全对齐交接包、项目并集、任务清单、有效侧边栏布局和两台设备映射。
2. 先发布当前设备新发现的项目，再计算最新并集。
3. Windows 设备确认所有并集项目位于 `D:\.aaProject-Bruce\`；不得在 C 盘创建共同项目。
4. 按“逻辑项目 ID + 显示名称 + 本地路径或远程仓库”匹配本机项目。
5. 对本机缺失项目，验证 Git 来源和目标路径，克隆全部组成仓库并校验 remote、默认分支、HEAD 和工作树。
6. 使用正式 Codex 项目管理能力添加真实项目根目录；不能修改 Codex 数据库伪造项目。
7. 回读本地 `projectId` 并写入当前设备映射。
8. 遍历任务并集，在对应已保存项目内补充全部缺失任务镜像；设置精确标题、发送本轮唯一合并包中的同一版精简交接，回读实际标题、项目归属和 `[SYNC-CONTEXT v1]` 正文并重算 SHA，再记录本地 `threadId` 和正文 SHA。缺少精确回读能力时记为未验证，不能凭请求成功报完成。
9. 四字口令“开始同步”继续按上节版本协议应用或发布共享侧边栏布局。
10. 只有项目并集、任务并集和逐任务语义交接全部完成，且本设备回执已逐项验证时，才标记为“已完整应用”；布局另行记录完整或部分应用，不能因项目或任务存在就误报排序和置顶完成。
11. 检查、提交、再次取得远端更新并推送。禁止强制推送。

## 阻塞项处理

- 先补齐所有未阻塞项目和任务镜像，并发送其精简语义交接。
- 项目来源、权限、本地路径或项目管理能力未就绪时，保留阻塞状态，不创建空壳。
- 每次用户发送“开始”或“开始同步”时重试阻塞项，即使清单版本没有变化。
- 另一台设备离线时，只能使用它最后推送的映射；明确说明并集是“截至最近交接”，不能声称看见其未推送本地状态。
- 阻塞解除并完成全部项目、任务镜像与交接后，才更新为目标清单版本。

## 绝对禁止

- 禁止为了两边一致而删除、归档、重命名或隐藏任何项目或任务。
- 禁止强制推送覆盖另一设备。
- 禁止把 A 的 `projectId` 或 `threadId` 当成 B 的本地 ID 使用。
- 禁止因路径暂缺而创建无内容的假项目。
- 禁止在 Windows 设备的 C 盘创建双设备共同项目。
- 禁止逐字复制原始聊天、附件缓存、数据库或 session；必须创建的是可见任务镜像，承载精准压缩后的可交接语义。
- 禁止把同名 Skill 目录冒充业务项目。

## 新项目处理

任一设备发现清单外项目时：

1. 保留原项目，不做清理。
2. 核实真实项目根目录及所有组成 Git 仓库。
3. 把项目、clone 地址、默认分支和当前阻塞加入并集清单与设备映射。
4. 推送上下文，交接通知另一端。
5. 另一端下次“开始同步”时把项目克隆到规定根目录并加入 Codex 项目列表。

如果项目暂时没有可用 Git 来源，先登记为阻塞；不得丢弃，也不得声称另一端已同步。

## 共同范围缩减

只有用户明确把项目或任务移出同步范围时：

1. 更新清单和范围说明。
2. 已有本地项目、任务及历史记录全部保留。
3. 另一台设备不再补建该项。
4. 范围缩减绝不构成删除、归档、重命名或隐藏授权。

所以这里的“完全统一”指：

> 除明确排除项外，截至两端最近一次成功发布的项目与任务并集，在 A、B 两台设备上全部真实存在并完成本地映射；每个任务都可见并具有最新精简交接语义，共享顺序和置顶也已验证。

A、B 的本地 `projectId`、`threadId` 和平台路径不要求相同；逻辑 ID、显示名称、项目内容来源、任务归属和精简交接语义必须一致。
