# 项目并集和任务列表增量对齐规则

## 目标

让 A、B 两台设备包含相同且最完整的可同步项目集合，同时绝不通过删除现有内容获得表面一致。

项目公共范围定义为：

> A 的可同步项目列表 ∪ B 的可同步项目列表

任一设备出现新项目，除明确排除项外，都要登记为并集项目，补充真实 Git 来源，并在另一台设备补齐。任务不采用全量并集；只有 `任务清单.md` 中的长期任务需要两端共同存在，临时会话继续不同步。

## 发布本机项目清单

1. 拉取 `CodexMissionContext` 最新版本。
2. 使用 Codex 项目列表能力读取本机实际项目；能力不可用时标记“部分覆盖”，不得凭记忆声称完整。
3. 对每个可同步本地项目记录逻辑 ID、显示名称、真实根目录、本地 `projectId`、包含的全部 Git 仓库、remote 和默认分支。
4. 本机项目尚未出现在 `项目清单.md` 时，直接把它加入并集；不再长期保留为只报告的“额外项目”。
5. 将本机映射、并集清单版本、新增项目及其取得方式提交并推送，使另一台设备能够发现。
6. `AI学习` 继续按最高优先级排除；账号级且没有本地 Git 路径的云项目只记录说明，不作为克隆目标。

没有 remote、权限或可传递来源的项目仍进入并集的待补齐状态，但不得创建空壳冒充完成。来源准备好后再由另一端实际克隆。

## 侧边栏布局对齐

项目实体采用 A、B 并集；共享侧边栏布局采用 `同步清单/侧边栏布局.md` 中带版本的最新有效发布状态。布局只包含逻辑 ID，不复制 Codex 原始本地状态；“已发布”与“已应用”分别记账。

用户发送四字口令“开始同步”时：

1. 先拉取布局状态和当前设备已应用版本。只有标记“有效”的规范布局可以自动应用。当前设备落后时，依据设备记录引用的不可变候选快照和 SHA-256 摘要重建本机上次确认的完整或部分应用基线，再与当前可见共享布局比较；已有非零基线且本地已偏离时，把本地状态保存为并发候选并停止自动应用。基线为 `0` 的首次对齐按远端有效版本执行，但用户明确要求保留本机当前布局时，先保存候选并停止；快照或摘要无法校验时也不得自动覆盖。
2. 只对共同项目同步项目置顶顺序和非置顶顺序；只对共同长期任务同步置顶顺序。`AI学习`、个人任务、临时任务和账号级云项目保持本机原样并从比较中排除。
3. 形成下一版本候选有两个并列条件：其一，当前设备已完整应用最新布局且用户当前可见的共享布局发生明确变化；其二，当前设备仍缺少并集对象，但其余可见共享对象已经按最新布局验证，缺失对象保持上一版本的置顶区域及其相对每个既有共享对象的前后关系，当前变化明确，且没有同基线并发冲突。第二种情况不得从部分视图移动缺失对象，发布设备仍按已部分应用记账。首次由触发“开始同步”的设备形成版本 `1` 候选。
4. 源设备暂缺的既有并集项目必须保持上一版本的置顶/非置顶区域，并保持它与每个仍存在共享项目的相对前后关系；不能唯一保留时停止发布。新项目没有既有位置时追加到非置顶区末尾。目标设备只收到新版本时记为待应用；实际尝试后缺少项目或任务才记为已部分应用。单纯应用远端版本时不回发残缺布局。
5. 使用稳定合并应用共享顺序：非共享项目和任务的置顶状态保持不变，它们在各自置顶区和非置顶区内的相对顺序保持不变；只重排共享对象形成的子序列。工具只能整体重排而无法保证这一边界时，标记部分应用且不执行。
6. 应用必须通过正式 Codex API 或用户可见界面完成。正式列表能力不暴露排序或置顶时，只允许只读提取 `project-order`、`pinned-project-ids` 和 `pinned-thread-ids` 并转换为逻辑 ID；严禁提交或写回 Codex 原始状态、数据库、session 或缓存。
7. 每台设备分别记录 `设备状态确认来源与时间`、`已完整应用侧边栏布局版本`、`已部分应用侧边栏布局版本`、`本设备已确认待应用版本`、`已部分应用未完成逻辑 ID` 和 `本机上次确认布局基线`。只有目标设备实际拉取后才能由该设备写“已确认待应用”；发布端另记“待目标设备获取版本”和预期阻塞，不能替目标设备预报收件或应用结果。实际尝试并只完成一部分时才更新已部分应用；全部共享对象验证成功后才提升完整版本并清空其余状态。
8. 排序和置顶授权不包括删除、归档、重命名、隐藏项目或任务。新布局按 `同步清单/侧边栏布局候选/README.md` 两阶段发布：先单独推送候选，再 fetch；只有远端规范仍为前序版本且同基线候选唯一时，第二次提交才提升为有效下一版本。晋升前有竞争候选时规范保持前序版本；晋升后才出现迟到的同基线候选时，不回滚已应用设备，把当前规范标记“冲突待裁决”并暂停继续应用，等待用户选择或明确合并成再下一版本。

## 一次对齐流程

1. 拉取最新项目并集、任务清单和两台设备映射。
2. 先发布当前设备新发现的项目，再计算最新并集。
3. Windows 设备确认所有并集项目位于 `D:\.aaProject-Bruce\`；不得在 C 盘创建共同项目。
4. 按“逻辑项目 ID + 显示名称 + 本地路径或远程仓库”匹配本机项目。
5. 对本机缺失项目，验证 Git 来源和目标路径，克隆全部组成仓库并校验 remote、默认分支、HEAD 和工作树。
6. 使用正式 Codex 项目管理能力添加真实项目根目录；不能修改 Codex 数据库伪造项目。
7. 回读本地 `projectId` 并写入当前设备映射。
8. 只在任务清单规定的项目内补充缺失长期任务；设置精确标题并记录本地 `threadId`。
9. 四字口令“开始同步”继续按上节版本协议应用或发布共享侧边栏布局。
10. 只有项目并集和长期任务清单全部完成时，才标记为“已完整应用”；布局另行记录完整或部分应用，不能因项目存在就误报排序和置顶完成。
11. 检查、提交、再次取得远端更新并推送。禁止强制推送。

## 阻塞项处理

- 先补齐所有未阻塞项目及长期任务。
- 项目来源、权限、本地路径或项目管理能力未就绪时，保留阻塞状态，不创建空壳。
- 每次用户发送“开始”或“开始同步”时重试阻塞项，即使清单版本没有变化。
- 另一台设备离线时，只能使用它最后推送的映射；明确说明并集是“截至最近交接”，不能声称看见其未推送本地状态。
- 阻塞解除并完成全部项目与任务后，才更新为目标清单版本。

## 绝对禁止

- 禁止为了两边一致而删除、归档、重命名或隐藏任何项目或任务。
- 禁止强制推送覆盖另一设备。
- 禁止把 A 的 `projectId` 或 `threadId` 当成 B 的本地 ID 使用。
- 禁止因路径暂缺而创建无内容的假项目。
- 禁止在 Windows 设备的 C 盘创建双设备共同项目。
- 禁止把最近临时对话批量复制成任务。
- 禁止把同名 Skill 目录冒充业务项目。

## 新项目处理

任一设备发现清单外项目时：

1. 保留原项目，不做清理。
2. 核实真实项目根目录及所有组成 Git 仓库。
3. 把项目、clone 地址、默认分支和当前阻塞加入并集清单与设备映射。
4. 推送上下文，交接通知另一端。
5. 另一端下次“开始同步”时把项目克隆到规定根目录并加入 Codex 项目列表。

如果项目暂时没有可用 Git 来源，先登记为阻塞；不得丢弃，也不得声称另一端已同步。

## 共同范围缩减

只有用户明确把项目或任务移出同步范围时：

1. 更新清单和范围说明。
2. 已有本地项目、任务及历史记录全部保留。
3. 另一台设备不再补建该项。
4. 范围缩减绝不构成删除、归档、重命名或隐藏授权。

所以这里的“完全统一”指：

> 除明确排除项外，截至两端最近一次成功发布的项目并集，在 A、B 两台设备上全部真实存在并完成本地映射。

A、B 的本地 `projectId`、`threadId` 和平台路径不要求相同；逻辑 ID、显示名称、项目内容来源和持久化上下文必须一致。
