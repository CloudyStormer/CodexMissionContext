## 用户要求

- 每位球员由影棚多相机拍摄 36 张多角度照片，单张约 5 MB，每组约 180 MB。
- 现状是操作设备从影棚主机内网下载后再上传云端；未传完时影棚不能拆除。
- 要求拍完每组即开始本地保存，浏览器不卡、页面关闭不影响传输；本轮只做设计，不编码。

## 代码事实

- 当前高清照片不落盘。`scanPhotoSync.js` 默认从影棚下载 3 路、云上传 3 路、最多缓冲 6 张；任务生命周期仍绑定标签页。
- `downloadPlayerImageFile` 将单图整体转成 Blob/File，执行 JPEG 头尾、解码和 SHA-256 校验，再 multipart 上传 `/socket/fifa/player/uploadImageV2`。
- 拍摄主链调用固定影棚主机 `https://192.168.88.2:8200`；`/startTakePhoto` 返回 `photo_id`，`/photoUrlList?file_type=2` 返回高清照片 URL。
- 预览组件对全组图片独立 `fetch -> blob -> object URL`，36 张编码数据约 180 MB 且另有解码内存；未做缩略图复用或预览限流。
- 任务状态 `4 / Scanned` 的现有文案明确表示照片仍在扫描仪、未上云；Sync 按钮还受当前影棚 `equipmentId` 和内网门禁。
- `fetchUploadState` 调用时传了 `reconcile: true`，但 API 封装未发送该参数，不能把现有 status 接口当作已验证的权威云端对账协议。

## 架构决定

- 生产方案选“操作笔记本真实磁盘 + 独立 Studio Transfer Agent 系统服务”，不把 IndexedDB/OPFS 当照片唯一真源。浏览器只发送小 JSON 命令并通过 SSE 展示状态，照片字节不再进入 JS Heap。
- IndexedDB 只用于少量 UI/任务元数据。若不得不做纯浏览器 POC，选 OPFS + Dedicated Worker + `navigator.storage.persist()`，但必须显示“不能作为拆棚安全承诺”。
- 拍摄取得 `photo_id` 后立即在 Agent 幂等登记 `PROVISIONAL` 批次；Agent 与合规检测并行拉取高清图。用户 Save & Scan Next 成功后将批次标记 `ACCEPTED`，重拍则 `RETAKE/CANCELLED`。
- Agent 将单图流式写入 `.part`，边写边算 SHA-256，校验长度/JPEG/可解码性后 `fsync` + 原子改名，再用 SQLite WAL 事务持久化状态。
- 本地状态达到 `LOCAL_DURABLE` 只表示操作设备已有完整副本；云端状态另行从 `PENDING -> UPLOADING -> VERIFYING -> COMPLETE`。只有所有已接受批次都为 `LOCAL_DURABLE`、无 `.part`/失败/未决定批次且 Agent/磁盘健康，才能给出“影棚可拆”。
- 每张约 5 MB，第一阶段以“单图级续传”即可，不打 180 MB ZIP；未来单图显著增大时再做对象存储分块续传。

## 容量与调度基线

- 原始日容量约为 `0.18 GB × 球员数`：200 人约 36 GB，300 人约 54 GB，500 人约 90 GB。
- Spool 建议容量为 `0.18 × 日人数 × 可承受云中断天数 × 1.2 GB`。300 人/天且中断 3 天约 194.4 GB，7 天约 453.6 GB；独立 512 GB SSD 为起步，多日离线建议 1 TB NVMe。
- 300 人在 10 小时内上传，按 80% 有效利用率需约 15 Mbps 持续上行；500 人需约 25 Mbps。云上传带宽应限制在可用上行的 60%–70%，影棚本地拉取优先。
- 水位按“还能拍多少批次”计算；红色水位在开始下一次拍摄前阻止新批次，绝不删除未完成云端校验的照片解除水位。

## 安全、API 与分阶段

- Agent 仅绑定 loopback，使用 HTTPS、Origin allowlist 与一次性握手令牌；照片目录使用 BitLocker/FileVault 或等价加密与专用 ACL，不记录球员姓名、签名 URL 或 token。
- 本地 API 核心为 `GET /v1/health`、`GET /v1/capacity`、幂等 `POST /v1/captures`、`POST /v1/captures/{id}/accept|retake|retry`、`GET /v1/captures/{id}` 与 SSE `GET /v1/events`。
- 第一阶段复用影棚 `/photoUrlList` 和现有逐图云上传语义，但 Agent 需独立、受限、短期的设备上传凭证，不得复用浏览器 Cookie。第二阶段再引入上传 Session、预签名对象 URL/短期 SAS、幂等 Finalize 和权威对账。
- 第三阶段完成签名安装包、自动更新、中央监控、磁盘预测、拆棚报告与故障注入演练。
