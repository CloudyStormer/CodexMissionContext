# 检查项目

把本技能作为 A、B 两台设备的项目协作入口。项目共享范围采用并集：除明确排除项外，A 有的项目 B 也要有，B 有的项目 A 也要有；不通过删除获得一致。

## 判断运行模式

- **项目提交模式**：用户以命令方式发送“检查提交”“检查项目”“项目检查”或“项目提交”，或者明确要求检查所有项目是否已提交推送。
- **完整同步模式**：用户发送四字口令“开始同步”。先读取 `同步清单/完全对齐交接包.md`，为本轮生成唯一同步运行 ID；若另一设备的维护任务可连接，只发送一次同轮执行请求。A、B 各自刷新项目与任务并集，对本机全部共同项目执行完整双向 Git 同步；随后补齐全部同步范围任务的可见镜像、把同一版精简语义正文及摘要送达两端、验证确定性共享布局，最后合并同一运行 ID 的两端回执。
- **开始模式**：用户单独发送“开始”。同步上下文，核对两端项目并集、补齐本机缺失项目并拉取远端。
- **交接模式**：用户要求“交接”“晚间交班”“下班交接”或汇报今天完成、新增及对方待办。先执行项目提交模式，再写入并推送精准交接记录，最后通知另一端。

这些模式只由用户主动触发，不创建定时任务，不在后台轮询。完整同步模式把两端同步范围任务取并集，缺失任务必须在另一端对应已保存项目中创建为可见镜像，并发送完整但精简的语义交接；不复制原始聊天全文或本地会话数据库。“所有任务”不表示擅自继续尚未获得授权的业务遗留需求。其他模式不枚举无关任务。

## 统一执行与确认

- 每台设备始终只由一个“双设备同步维护”任务直接处理本机所有共同项目仓库；A、B 在同一运行 ID 下各执行一个维护任务属于双端同步，不属于逐项目分派。不得为 Git 操作逐项目创建、唤醒或转交独立 Codex 任务。
- 把用户的一次触发口令视为对相应模式内普通 Git 操作的整体授权；不要为每个仓库的 fetch、pull、commit 或 push 重复询问。
- 可并行执行只读盘点，但需要写入 `.git` 或远端的动作仍由当前同步任务统一执行和复核。
- 若平台强制要求当前任务无法自行满足的交互授权，不连续创建逐仓确认；完成其余无需授权的工作后，把所有受阻仓库和唯一所需动作合并报告一次。

## 双端同轮协调

1. 每次“开始同步”生成唯一同步运行 ID，至少包含发起设备和时间。所有上下文报告、对端请求和最终结论都引用该 ID。
2. 已知另一设备维护任务且通信能力可用时，只发送一次包含运行 ID、发起设备、完整同步要求和“不要反向派发”的执行请求；发起端同时继续本机流程，不等待逐项目确认。对端收到请求后沿用同一 ID 执行本机流程，不再反向唤醒，避免 A/B 循环。
3. 对端任务或主机不可达时，记录“对端未参与本轮”并继续当前设备；不得据一端的远端引用推断另一端尚未推送的本地文件、提交或任务状态。
4. 当前设备结束前再次取得 `CodexMissionContext` 远端状态并收集同一运行 ID 的对端报告。只有两端报告均已取得、两端代码检查范围全部与 upstream 一致、项目与任务并集已补齐、每个任务的精简交接已送达且共享顺序与置顶已验证，才可回答“两端全部同步”；否则只报告当前设备结果和双端剩余项。

## 四字口令“开始同步”

“开始同步”不是普通任务开始提示，而是用户要求的完整同步口令。执行时必须：

1. 按“双端同轮协调”生成同步运行 ID，并尝试一次性启动另一设备的维护任务。
2. 先取得 `CodexMissionContext` 最新远端事实。上下文工作树干净时直接拉取；已有修改时只 fetch，并用远端引用读取清单、`同步清单/完全对齐交接包.md` 与布局，整合、提交和推送留到最后，绝不覆盖本地记录。按 `同步运行/README.md` 建立本轮运行目录。
3. 刷新项目列表，发布本机新增项目，计算 A/B 项目并集，并补齐本机缺失项目。
4. 使用当前 Codex 的任务列表能力刷新本地任务、可连接远程主机任务和账号级线上任务；按刷新后的项目并集遍历所有同步范围任务，不限当天或是否登记为长期任务，生成稳定逻辑任务 ID 和完整语义交接。A、B 分别发布本机任务快照，发起端取得两端快照后生成唯一合并任务包；按 A∪B 任务并集，在目标设备对应已保存项目中补齐缺失镜像，设置精确标题并发送合并包中同一版精简正文。创建或更新后必须再次读取正式任务列表，确认任务实际可见、标题和项目归属正确；补齐新项目后也必须再扫一次其可见任务。
5. 若某台设备或线上来源不可达，明确记录不可见范围；不得把离线设备尚未提交的本地任务或文件声称为已拉取。
6. 按 `同步清单/侧边栏布局.md` 的最新有效版本对齐共享项目与已纳入该版本的任务布局；只使用逻辑 ID 传递布局。交接包中的完整任务顺序在正式两阶段晋升前只是下一版本目标输入：先取得 A/B 完整任务快照和唯一合并包，再发布候选并晋升；晋升前只补任务实体和语义，不按候选任务顺序重排。
7. 第一阶段处理当前设备的全部共同项目仓库：逐仓执行下文正规提交流程的步骤 1—5，只检查并安全取得远端，禁止在此阶段暂存、提交或推送。远端已前进且工作树有改动时使用可恢复的保护 stash 对齐后再恢复，不得丢失本地内容。每个仓库必须先得到“远端取得完成”或“第一阶段阻塞”的明确结果；全部仓库都得到结果后，才可进入上传阶段。
8. 第二阶段只处理第一阶段完成的共同项目仓库：逐仓执行下文步骤 6—10，审查、验证、提交、再次 fetch、安全 rebase 并 push。已有未推送且可独立确认的提交也要上传；逐仓验证本地 `HEAD` 与 upstream 一致。第一阶段阻塞的仓库不得进入第二阶段。
9. 某仓库发生冲突、验证失败、来源不可达或内容不安全时保留现场并记录唯一阻塞，继续其他独立仓库。最后更新完整语义交接和同步记录，提交并推送上下文仓库，再取得并合并同一运行 ID 的对端报告。

## 任务实体与对话完整语义同步

- 遍历当前工具可见且属于共同项目的所有任务和对话；个人排除项目和不属于共同项目的 C 盘旧任务不读取正文。
- 优先读取任务标题、项目、状态、概述和最终结果；信息不足时只读取足以还原当前状态的最近轮次，不搬运整段原始对话。
- 按逻辑任务记录用户要求、结论、决定原因、文件、命令、测试、失败、风险、遗留问题和精确下一步，使另一端无需原始聊天也能继续。
- 每个同步范围任务都必须登记到 `任务清单.md` 和设备任务映射。目标端缺失时，在对应已保存项目创建同名可见镜像，并把合并后的精简交接实际发送到该任务；每日报告只是索引和本轮总览，不能代替任务实体。
- 可见任务暂时无法映射到逻辑项目时，登记为“项目归属待判定”的同步阻塞并保留其任务 ID；不得静默排除，也不得在错误项目或 projectless 位置创建替代品。
- 镜像任务的第一条或更新消息使用稳定结构：`当前目标 / 已完成 / 关键决定与原因 / 文件与命令 / 验证 / 失败与风险 / 下一步 / 原设备与更新时间`。按交接包规则规范化正文并计算 SHA-256，消息头写入运行 ID、逻辑任务 ID 和摘要；A、B 必须收到同一正文 SHA。创建镜像只授权导入上下文并等待用户继续，不授权执行旧需求。
- 发送或创建接口成功不构成验收。必须用正式任务读取能力回读 `[SYNC-CONTEXT v1]` 正文并重算 SHA，同时回读实际标题和项目归属；缺少精确正文读取或标题修改/验证能力时，把对应字段记为未知或失败，不能声称内容或实体完全一致。
- 原始逐字聊天、附件缓存、账号状态、数据库和 session 不复制；“对话一致”以语义完整且可直接续接为准。
- 对不可见主机、来源或未推送本地状态明确标记边界，不把摘要推断成已取得事实。

## 完全对齐交接包与运行回执

- `同步清单/完全对齐交接包.md` 固定当前项目目标顺序、完整任务目标顺序、语义正文格式、摘要算法和设备待办；“开始同步”每次都必须读取，普通每日同步不执行这套重型全量协议。
- 扫描发现交接包目标之外的新同步范围项目或任务时，当前运行目标立即过期：先更新并推送项目/任务清单、交接包目标修订、数量、顺序和摘要；两端拉取相同修订后用新运行 ID 重建完整快照。旧运行只保留为未完成审计，不得继续发布布局候选或完成回执。
- `同步运行/<运行ID>/A-任务快照.md` 与 `B-任务快照.md` 由各自设备独占写入；发起端只在取得两端快照后生成 `合并任务包.md`。两端正文 SHA 不同但事实兼容时，去重合并全部有效语义并生成唯一新正文和合并理由；存在不能同时成立的实质冲突时保留双方来源并把任务标为阻塞。不得只按时间戳静默覆盖。
- 两端都只能把 `合并任务包.md` 中的同一规范化正文发送给对应镜像。没有新语义且 SHA 未变化时不重复全文；为了排序验证发送的短检查点只引用已有 SHA。
- A/B 完整任务快照和唯一合并包先作为完整任务布局候选的发布输入；候选按两阶段协议晋升为有效布局后，两端才应用目标顺序并分别写入本机回执。回执逐项记录真实 `projectId`、`threadId`、标题、项目归属、置顶、共享索引和语义 SHA，并单独记录 expected/actual 的置顶项目序列、非置顶项目序列及 `project_layout_verified`，还要记录每个 Git 仓库最终提交与 upstream 状态。项目排序、置顶或回读能力缺失时把项目布局记为 `unknown`；任一回执不存在、未知或失败，本轮都未完成。
- 另一设备下次收到“开始同步”时，先读最近未完成运行和交接包，能安全续接则沿用已发布快照；不能取得同一运行 ID 的另一端回执时，不把历史快照冒充本轮双端完成。

## 维护项目并集

“公共项目”指 A、B 可同步项目的并集，而不是交集。

1. 使用当前 Codex 的项目列表读取能力获取本机实际项目；若能力不可用，使用当前设备映射，并把覆盖范围标记为“部分”。
2. 将本机新增项目写入当前设备映射，并登记到 `同步清单/项目清单.md`。读取项目根目录及其中全部 Git remote，记录可供另一设备取得内容的克隆地址。
3. 拉取另一设备已推送的项目映射和并集清单。对本机缺失的并集项目：
   - 先验证名称、目标目录和 Git 来源；
   - macOS 放在 `~/Desktop/DEV/Life/CodexSpace/` 下；
   - Windows 放在 `D:\.aaProject-Bruce\` 下，禁止在 C 盘创建共同项目；
   - 克隆项目的每个组成仓库，验证默认分支、remote、HEAD 和工作树；
   - 使用正式 Codex 项目管理能力把真实项目根目录加入项目列表；
   - 回读本地 `projectId` 并写入当前设备映射。
4. 某项目缺少路径、Git 来源、权限或项目管理能力时，登记阻塞并继续其他项目；不创建空壳、不猜测仓库、不把同名 Skill 目录冒充项目。
5. 完成后更新已应用版本。只有并集中的全部项目在本机真实存在并完成映射时，才标记“完整应用”。

永久排除 `AI学习`、`AI 教学助手`、`AI 笔记助手` 及其子目录，除非用户以后明确点名解除；没有本地 Git 路径的账号级云项目只报告，不克隆。不得删除、归档、重命名或隐藏任何现有项目。

## 对齐侧边栏布局

布局对齐只在四字口令“开始同步”中执行。项目并集仍采用只增不减；布局采用 `同步清单/侧边栏布局.md` 中带版本的最新有效发布状态。发布的是期望布局，不等于任何设备已经应用成功。

1. 拉取上下文后，读取共享布局版本、布局状态和当前设备已应用版本。只有标记为“有效”的规范布局可以自动应用；“冲突待裁决”的版本必须停止。
2. 当前设备落后于另一设备发布的布局时，先依据设备记录引用的不可变候选快照和 SHA-256 摘要，重建本设备上次确认的完整或部分应用基线，再与当前可见共享布局比较。若已有非零基线且本地布局已经偏离该基线，把它保存为并发候选并停止自动应用，不能静默覆盖；基线为 `0` 的首次对齐按远端有效版本执行，但用户明确要求保留本机当前布局时，先保存候选并停止自动应用。基线快照或摘要缺失、校验失败时同样停止自动覆盖并报告。没有本地偏离时再把远端布局应用到本机，不得用本机旧顺序反向覆盖：
   - 将逻辑项目 ID 映射成本机 `projectId`；
   - 依次应用项目置顶顺序和非置顶顺序；
   - 对 `任务清单.md` 中全部同步范围任务应用置顶状态和共享子序列；
   - 缺少项目、任务或正式管理能力时，实际尝试后标记“已部分应用”，保留未能应用的逻辑位置；仅收到新版本但尚未尝试时只记“待应用”，不能预报为部分应用；任务创建后必须回读正式列表确认实际显示，不能只凭创建请求成功推断已应用；
   - 单纯应用远端版本时不得回发一份由部分视图生成的新布局。
3. 形成下一版本候选分为三个并列分支：
   - 当前设备已完整应用最新布局，且用户当前可见的共享布局发生明确变化；
   - 当前设备仍缺少并集对象，但其余可见共享对象已经按最新布局验证，缺失对象的置顶区域及其相对每个既有共享对象的前后关系全部沿用上一版本，当前变化明确，且没有同基线并发冲突。此分支不得从部分视图改变缺失对象的位置，发布设备仍按“已部分应用”记账。
   - **完整任务并集迁移**：任务清单从旧的部分任务基线扩展为完整并集时，已取得同一运行 ID 的 A/B 完整任务快照、唯一合并任务包和交接包规范化目标摘要；合并包内全部逻辑任务必须恰好各出现一次且 `merge_state` 全为 `READY`。候选必须记录来源运行 ID、两份快照文件 SHA、合并包文件 SHA、交接包目标修订和目标顺序 SHA，且全部校验通过；READY 记录中的单端来源 SHA `MISSING` 表示正常待补镜像，不阻塞候选，只有 `merge_state` 非 `READY`、任务缺项/重复或候选来源文件校验失败才禁止进入候选。候选覆盖全部任务，保留旧布局已登记任务的置顶区域及相对顺序，新纳入任务按交接包的确定性项目分组顺序插入。此分支不要求发布端先应用尚不存在的新布局，也不要求晋升后的顺序回执作为候选前提。
   首次没有布局记录时，由触发“开始同步”的设备形成版本 `1` 候选。
4. 候选生成前只过滤 `AI学习`、`AI 教学助手`、`AI 笔记助手`、明确排除的个人任务和账号级云项目；共同项目内的临时任务不再过滤。置顶与非置顶的共享项目、任务分别按界面从上到下记录；源设备缺少的既有并集对象必须保持上一版本区域及相对关系。任何关系无法唯一保留时停止并报告歧义。普通分支中新对象没有既有位置时追加到对应非置顶区末尾；“完整任务并集迁移”分支的新任务改按交接包目标插入，但仍必须保留全部旧任务的相对顺序。
5. 若正式项目列表能力不返回顺序或置顶，可只读提取 Codex 本地状态中的 `project-order`、`pinned-project-ids` 和 `pinned-thread-ids`，再通过设备映射转换成逻辑 ID；严禁复制、提交或写回原始全局状态、数据库或 session。
6. 最新有效布局若已经包含完整任务顺序，且正式任务列表明确保证非置顶任务按最近更新时间返回、目标任务全部非置顶，可尝试“最近更新规范化”：以相同语义 SHA 的短检查点按有效布局顺序从下到上串行处理，逐项等待完成，期间不并发更新其他共享任务。调用任务自身、活动任务完成时间或其他并发更新会破坏确定性时不使用；执行后必须回读并逐项验证共享子序列，验证失败仍为部分应用。候选晋升前不得按候选顺序执行；该方法不能推导多个置顶任务的内部顺序，也不能用于项目顺序。
7. 应用共享顺序时使用稳定合并：固定所有明确排除项目和任务的置顶状态，并保持它们在各自置顶区、非置顶区内的相对顺序；只重排共享对象形成的子序列。若工具只能整体重排而不能保证该边界，标记部分应用，不执行排序。
8. 应用布局必须使用正式 Codex API 或用户可见界面。不得直接编辑 Codex 本地数据库或全局状态文件。能力不可用时，推送期望布局和阻塞，让另一端下次重试。
9. 设备记账至少区分：`设备状态确认来源与时间`、`已完整应用侧边栏布局版本`、`已部分应用侧边栏布局版本`、`本设备已确认待应用版本`、`已部分应用未完成逻辑 ID` 和 `本机上次确认布局基线`。只有目标设备实际拉取后才能由该设备写“已确认待应用”；发布端只能另记“待目标设备获取版本”和已知预期阻塞，不能替另一端预报收件或应用结果。实际尝试并只完成一部分后才更新“已部分应用”；全部共享对象均验证成功后才提升完整版本并清空部分、待应用和未完成状态。发布端也按自身真实应用结果记账，不能把“已发布”当成“已应用”。
10. 新布局必须按 `同步清单/侧边栏布局候选/README.md` 两阶段发布：先生成包含规范化清单与摘要的独立候选，提交并推送，但不修改规范布局；再次 fetch，确认远端规范仍在前序版本且同基线只有一个候选后，第二次提交才把候选提升为“有效”的唯一下一版本。若晋升前发现竞争候选，规范文件保持前序版本；若有效版本发布后才发现基于其前序版本的迟到候选，不回滚已应用设备，而把当前规范版本标记“冲突待裁决”，暂停未应用设备继续应用，等待用户选择或明确合并成再下一版本。

用户的这项授权只允许补齐同步范围任务镜像，并对共享项目和任务进行排序、置顶或取消置顶；不允许删除、归档、重命名或隐藏任何现有对象，也不允许复制明确排除的个人项目与任务。

## 发现项目中的全部仓库

不要把一个项目等同于一个仓库。项目根目录本身以及其下的独立 Git 工作树都要检查；例如 `lottery` 必须覆盖前端和后端两个仓库。

把已解析出的项目根目录交给只读盘点脚本。以下命令从 `CodexMissionContext` 根目录运行：

```bash
bash 全局技能/check-projects/scripts/inspect-project-repos.sh --fetch "/项目根目录一" "/项目根目录二"
```

脚本只发现仓库、刷新远端引用并输出状态，不会修改工作树、创建提交或推送。

先处理业务仓库，最后处理 `CodexMissionContext`。嵌套仓库先处理更深层的仓库，再处理父仓库。

## 项目提交与完整同步共用的正规提交流程

以下步骤适用于四字口令“开始同步”、“检查提交”“检查项目”“项目检查”“项目提交”和交接模式中的项目提交阶段。单独“开始”仍只补齐项目并集和取得远端，不提交或推送业务仓库。

完整同步模式必须服从全局两阶段屏障：先对每个仓库执行步骤 1—5，并把不可达、冲突或恢复失败记为第一阶段阻塞；等所有仓库都得到第一阶段结果后，只对已完成者执行步骤 6—10。其他提交模式可逐仓端到端执行步骤 1—10。

对每个仓库先读取适用的 `AGENTS.md`，再执行：

1. 检查当前分支、upstream、remote、merge/rebase 状态和冲突。
2. 运行 `git fetch --all --prune`，先取得远端最新状态。
3. 检查工作树、暂存区、未跟踪文件、`git diff` 和 `git diff --cached`。
4. 工作树干净时先用 fast-forward 或非交互式 rebase 取得远端最新提交。
5. 工作树有修改且远端也前进时，先盘点本地改动并确认能够安全保护，再创建带时间标识的命名 stash（包含已跟踪和未跟踪改动）；拉取远端后用 `stash apply` 恢复。恢复冲突时保留 stash 和现场并阻塞；完整内容审查留在第二阶段，只有恢复内容已经成功提交后才删除该 stash。
6. 检查 `.env`、`auth.json`、令牌、密码、Cookie、SSH 私钥、数据库、session、缓存、异常大文件和明显生成垃圾。发现疑似敏感或误入内容时，本轮默认暂停该仓库全部上传，不把同仓其他提交当成已安全；保留现场并报告凭证轮换或内容隔离需求。
7. 运行仓库已有且与改动相称的验证。验证失败时，本轮暂停该仓库全部上传并保留完整错误；不要顺带推送该仓库既有未推送提交。
8. 暂存全部确认安全的项目改动，按实际内容编写描述性提交信息；互不相关的内容拆成独立提交。
9. 再次 fetch；如远端出现新提交，只允许对尚未发布的本地提交做安全 rebase，绝不改写 upstream 或任何已发布历史。发生冲突立即中止 rebase，并保留本地提交。
10. 推送当前分支。push 遇到远端竞态时，重新 fetch，并仍只对尚未发布的本地提交 rebase，最多重试一次。

“开始同步”和“项目提交”均授权处理检查范围内已有的普通项目改动，不限于当前对话产生的文件；无需为每个普通提交重复确认。但这不授权删除项目、改写 upstream 或已发布历史、泄露凭证、绕过失败验证或掩盖冲突；只允许为安全对齐远端而 rebase 尚未发布的本地提交。无法安全确认的改动必须保留并使该仓库标记为未完全同步，不得为了追求全绿而盲目上传。

upstream 缺失时，只有 remote 和目标分支唯一明确才使用 `git push -u`；否则阻塞。禁止 force push、`reset --hard`、`clean`、删除项目或切换到不明分支。一个仓库阻塞时继续检查其他独立仓库。

## 处理上下文与交接

`CodexMissionContext` 最后处理。更新项目与任务并集清单、完全对齐交接包、设备映射、本轮任务快照/合并包/回执、逐任务精简交接、项目稳定事实及必要的长期任务记录后运行：

```bash
./脚本/检查仓库.sh
./脚本/同步上下文.sh 结束 "检查项目：项目同步与交接"
```

交接记录使用中文精准压缩，至少包括：

- 当天处理过的项目和各仓库最终提交；
- 新增项目、克隆地址、项目组成和本地映射；
- 已完成的工作与验证结果；
- 另一设备需要拉取、安装、补建或继续的事项；
- 冲突、权限、网络、缺少 remote 等阻塞；
- 下一位同事可以直接执行的精确步骤。

上下文推送成功后，使用可用的 Codex 任务通信能力向另一设备的“双设备同步维护”任务发送同一运行 ID 的简短完成通知；如果本轮执行请求已经确认送达，这只是结果通知，不得再次要求对端反向启动。只有工具确认送达时才声称已通知；不可达时说明原因，并以远端上下文仓库作为待对方下次“开始同步”时读取的权威交接。

## 最终复核

再次刷新远端引用并逐仓确认：

- 工作树是否干净；
- 是否仍有未推送提交或落后 upstream；
- 最终分支与提交 SHA；
- 验证、提交、拉取和推送结果；
- 无法处理的精确原因。
- 共享侧边栏布局的发布版本、已应用版本、项目与全部同步范围任务的置顶/排序结果。
- 所有同步范围任务是否已在两端可见，逐任务精简语义交接是否已实际送达。
- A、B 任务回执中交接包当前全部逻辑任务的语义正文 SHA、共享任务索引和项目共享子序列是否逐项相同，且回执引用的有效布局版本及 SHA 是否一致。

最终按项目和仓库报告 `已是最新 / 已拉取 / 已提交并推送 / 阻塞`，同时报告两端项目并集、任务并集、逐任务语义镜像和共享侧边栏布局是否完整。当前设备只有全部检查范围内仓库都与 upstream 一致、没有未处理的安全普通改动，且本机应有任务实体、语义与布局均验证成功时，才可回答“当前设备全部同步”；回答“两端全部同步”还必须取得同一运行 ID 的两端成功报告。任一项阻塞就直接回答“没有全部同步”并列出剩余项。明确说明一台设备无法发现另一台离线设备尚未提交到 Git 的本地文件或未发布任务状态。
