# 检查项目

把本技能作为 A、B 两台设备的项目协作入口。项目共享范围采用并集：除明确排除项外，A 有的项目 B 也要有，B 有的项目 A 也要有；不通过删除获得一致。

## 判断运行模式

- **项目提交模式**：用户以命令方式发送“检查提交”“检查项目”“项目检查”或“项目提交”，或者明确要求检查所有项目是否已提交推送。
- **完整同步模式**：用户发送四字口令“开始同步”。先同步上下文并读取当前 Codex 能访问的本地、远程和账号级线上任务状态，再核对两端项目并集、补齐本机缺失项目，对齐共享项目顺序和置顶状态，并拉取当前设备全部项目仓库的远端最新提交。
- **开始模式**：用户单独发送“开始”。同步上下文，核对两端项目并集、补齐本机缺失项目并拉取远端。
- **交接模式**：用户要求“交接”“晚间交班”“下班交接”或汇报今天完成、新增及对方待办。先执行项目提交模式，再写入并推送精准交接记录，最后通知另一端。

这些模式只由用户主动触发，不创建定时任务，不在后台轮询。完整同步模式只刷新任务元数据、概述和结果；不复制原始聊天或本地会话数据库。其他模式不枚举临时任务。

## 四字口令“开始同步”

“开始同步”不是普通任务开始提示，而是用户要求的完整同步口令。执行时必须：

1. 拉取 `CodexMissionContext` 最新远端提交，解决双方可安全合并的记录；冲突时保留两边事实。
2. 使用当前 Codex 的任务列表能力刷新本地任务、可连接远程主机任务和账号级线上任务；记录标题、项目、状态、概述和最终结果，不复制原始对话。
3. 若某台设备或线上来源不可达，明确记录不可见范围；不得把离线设备尚未提交的本地任务或文件声称为已拉取。
4. 刷新项目列表，发布本机新增项目，计算 A/B 项目并集，并补齐本机缺失项目。
5. 按 `同步清单/侧边栏布局.md` 的版本协议，对齐共享项目的置顶顺序、非置顶顺序和共同长期任务的置顶顺序；只使用逻辑 ID 传递布局。
6. 发现当前设备每个项目根目录及其全部 Git 仓库，先 fetch；只有工作树干净且能 fast-forward 时才拉取。本地存在修改时只报告并保留现场，不 stash、不暂存、不提交、不推送。
7. 最后更新同步记录并推送上下文，使另一端下次执行同一口令时能取得本次完整状态。

## 定位协作仓库

`CodexMissionContext` 固定位置：

- macOS：`~/Desktop/DEV/Life/CodexSpace/CodexMissionContext`
- Windows：`D:\.aaProject-Bruce\CodexMissionContext`

识别 `.device-id` 后读取：

1. `同步清单/项目清单.md`
2. `同步清单/增量对齐规则.md`
3. `同步清单/侧边栏布局.md`
4. `设备/A/项目映射.md`
5. `设备/B/项目映射.md`
6. 当前设备的已应用清单与布局版本

上下文仓库干净时先运行 `脚本/同步上下文.sh 开始`。若它已有修改，不要 reset 或覆盖；先 `fetch` 获取远端事实，把该仓库留到最后处理。

## 维护项目并集

“公共项目”指 A、B 可同步项目的并集，而不是交集。

1. 使用当前 Codex 的项目列表读取能力获取本机实际项目；若能力不可用，使用当前设备映射，并把覆盖范围标记为“部分”。
2. 将本机新增项目写入当前设备映射，并登记到 `同步清单/项目清单.md`。读取项目根目录及其中全部 Git remote，记录可供另一设备取得内容的克隆地址。
3. 拉取另一设备已推送的项目映射和并集清单。对本机缺失的并集项目：
   - 先验证名称、目标目录和 Git 来源；
   - macOS 放在 `~/Desktop/DEV/Life/CodexSpace/` 下；
   - Windows 放在 `D:\.aaProject-Bruce\` 下，禁止在 C 盘创建共同项目；
   - 克隆项目的每个组成仓库，验证默认分支、remote、HEAD 和工作树；
   - 使用正式 Codex 项目管理能力把真实项目根目录加入项目列表；
   - 回读本地 `projectId` 并写入当前设备映射。
4. 某项目缺少路径、Git 来源、权限或项目管理能力时，登记阻塞并继续其他项目；不创建空壳、不猜测仓库、不把同名 Skill 目录冒充项目。
5. 完成后更新已应用版本。只有并集中的全部项目在本机真实存在并完成映射时，才标记“完整应用”。

永久排除 `AI学习` 及其子目录，除非用户以后明确点名解除；没有本地 Git 路径的账号级云项目只报告，不克隆。不得删除、归档、重命名或隐藏任何现有项目。

## 对齐侧边栏布局

布局对齐只在四字口令“开始同步”中执行。项目并集仍采用只增不减；布局采用 `同步清单/侧边栏布局.md` 中带版本的最新有效发布状态。发布的是期望布局，不等于任何设备已经应用成功。

1. 拉取上下文后，读取共享布局版本、布局状态和当前设备已应用版本。只有标记为“有效”的规范布局可以自动应用；“冲突待裁决”的版本必须停止。
2. 当前设备落后于另一设备发布的布局时，先依据设备记录引用的不可变候选快照和 SHA-256 摘要，重建本设备上次确认的完整或部分应用基线，再与当前可见共享布局比较。若已有非零基线且本地布局已经偏离该基线，把它保存为并发候选并停止自动应用，不能静默覆盖；基线为 `0` 的首次对齐按远端有效版本执行，但用户明确要求保留本机当前布局时，先保存候选并停止自动应用。基线快照或摘要缺失、校验失败时同样停止自动覆盖并报告。没有本地偏离时再把远端布局应用到本机，不得用本机旧顺序反向覆盖：
   - 将逻辑项目 ID 映射成本机 `projectId`；
   - 依次应用项目置顶顺序和非置顶顺序；
   - 只对 `任务清单.md` 中共同长期任务应用置顶顺序；
   - 缺少项目、任务或正式管理能力时，实际尝试后标记“已部分应用”，保留未能应用的逻辑位置；仅收到新版本但尚未尝试时只记“待应用”，不能预报为部分应用；
   - 单纯应用远端版本时不得回发一份由部分视图生成的新布局。
3. 形成下一版本候选分为两个并列分支：
   - 当前设备已完整应用最新布局，且用户当前可见的共享布局发生明确变化；
   - 当前设备仍缺少并集对象，但其余可见共享对象已经按最新布局验证，缺失对象的置顶区域及其相对每个既有共享对象的前后关系全部沿用上一版本，当前变化明确，且没有同基线并发冲突。此分支不得从部分视图改变缺失对象的位置，发布设备仍按“已部分应用”记账。
   首次没有布局记录时，由触发“开始同步”的设备形成版本 `1` 候选。
4. 候选生成前过滤 `AI学习`、个人任务、临时任务和账号级云项目。置顶项目与非置顶项目分别按界面从上到下记录；源设备缺少的既有并集项目必须保持上一版本的置顶/非置顶区域，并保持它与每个仍存在共享项目的相对前后关系。任何关系无法唯一保留时停止并报告歧义。新项目没有既有位置时追加到非置顶区末尾。
5. 若正式项目列表能力不返回顺序或置顶，可只读提取 Codex 本地状态中的 `project-order`、`pinned-project-ids` 和 `pinned-thread-ids`，再通过设备映射转换成逻辑 ID；严禁复制、提交或写回原始全局状态、数据库或 session。
6. 应用共享顺序时使用稳定合并：固定所有非共享项目和任务的置顶状态，并保持它们在各自置顶区、非置顶区内的相对顺序；只重排共享对象形成的子序列。若工具只能整体重排而不能保证该边界，标记部分应用，不执行排序。
7. 应用布局必须使用正式 Codex API 或用户可见界面。不得直接编辑 Codex 本地数据库或全局状态文件。能力不可用时，推送期望布局和阻塞，让另一端下次重试。
8. 设备记账至少区分：`设备状态确认来源与时间`、`已完整应用侧边栏布局版本`、`已部分应用侧边栏布局版本`、`本设备已确认待应用版本`、`已部分应用未完成逻辑 ID` 和 `本机上次确认布局基线`。只有目标设备实际拉取后才能由该设备写“已确认待应用”；发布端只能另记“待目标设备获取版本”和已知预期阻塞，不能替另一端预报收件或应用结果。实际尝试并只完成一部分后才更新“已部分应用”；全部共享对象均验证成功后才提升完整版本并清空部分、待应用和未完成状态。发布端也按自身真实应用结果记账，不能把“已发布”当成“已应用”。
9. 新布局必须按 `同步清单/侧边栏布局候选/README.md` 两阶段发布：先生成包含规范化清单与摘要的独立候选，提交并推送，但不修改规范布局；再次 fetch，确认远端规范仍在前序版本且同基线只有一个候选后，第二次提交才把候选提升为“有效”的唯一下一版本。若晋升前发现竞争候选，规范文件保持前序版本；若有效版本发布后才发现基于其前序版本的迟到候选，不回滚已应用设备，而把当前规范版本标记“冲突待裁决”，暂停未应用设备继续应用，等待用户选择或明确合并成再下一版本。

用户的这项授权只允许对共享项目和共同长期任务进行排序、置顶或取消置顶；不允许删除、归档、重命名、隐藏或复制个人项目与临时任务。

## 发现项目中的全部仓库

不要把一个项目等同于一个仓库。项目根目录本身以及其下的独立 Git 工作树都要检查；例如 `lottery` 必须覆盖前端和后端两个仓库。

把已解析出的项目根目录交给只读盘点脚本：

```bash
bash scripts/inspect-project-repos.sh --fetch "/项目根目录一" "/项目根目录二"
```

脚本只发现仓库、刷新远端引用并输出状态，不会修改工作树、创建提交或推送。

先处理业务仓库，最后处理 `CodexMissionContext`。嵌套仓库先处理更深层的仓库，再处理父仓库。

## 仅用于项目提交模式的正规提交流程

以下步骤只适用于“检查提交”“检查项目”“项目检查”“项目提交”和交接模式中的项目提交阶段。四字口令“开始同步”和单独“开始”不得执行 stash、暂存、提交或推送业务仓库。

对每个仓库先读取适用的 `AGENTS.md`，再执行：

1. 检查当前分支、upstream、remote、merge/rebase 状态和冲突。
2. 运行 `git fetch --all --prune`，先取得远端最新状态。
3. 检查工作树、暂存区、未跟踪文件、`git diff` 和 `git diff --cached`。
4. 工作树干净时先用 fast-forward 或非交互式 rebase 取得远端最新提交。
5. 工作树有修改且远端也前进时，先完整审查本地改动，再创建带时间标识的命名 stash（包含已跟踪和未跟踪改动）；拉取远端后用 `stash apply` 恢复。恢复冲突时保留 stash 和现场并阻塞；只有恢复内容已经成功提交后才删除该 stash。
6. 检查 `.env`、`auth.json`、令牌、密码、Cookie、SSH 私钥、数据库、session、缓存、异常大文件和明显生成垃圾。疑似敏感或误入内容时不提交。
7. 运行仓库已有且与改动相称的验证。验证失败时不推送，并保留完整错误。
8. 暂存全部确认安全的项目改动，按实际内容编写描述性提交信息；互不相关的内容拆成独立提交。
9. 再次 fetch；如远端出现新提交，安全 rebase。发生冲突立即中止 rebase，并保留本地提交。
10. 推送当前分支。push 遇到远端竞态时，重新 fetch、rebase 后最多重试一次。

“项目提交”授权处理检查范围内已有的普通项目改动，不限于当前对话产生的文件；无需为每个普通提交重复确认。但这不授权删除项目、改写历史、泄露凭证、绕过失败验证或掩盖冲突。

upstream 缺失时，只有 remote 和目标分支唯一明确才使用 `git push -u`；否则阻塞。禁止 force push、`reset --hard`、`clean`、删除项目或切换到不明分支。一个仓库阻塞时继续检查其他独立仓库。

## 处理上下文与交接

`CodexMissionContext` 最后处理。更新并集清单、设备映射、项目稳定事实及长期任务记录后运行：

```bash
./脚本/检查仓库.sh
./脚本/同步上下文.sh 结束 "检查项目：项目同步与交接"
```

交接记录使用中文精准压缩，至少包括：

- 当天处理过的项目和各仓库最终提交；
- 新增项目、克隆地址、项目组成和本地映射；
- 已完成的工作与验证结果；
- 另一设备需要拉取、安装、补建或继续的事项；
- 冲突、权限、网络、缺少 remote 等阻塞；
- 下一位同事可以直接执行的精确步骤。

上下文推送成功后，使用可用的 Codex 任务通信能力向另一设备的“ 双设备同步维护 ”任务发送简短交接通知。只有工具确认送达时才声称已通知；不可达时说明原因，并以远端上下文仓库作为待对方下次“开始同步”时读取的权威交接。

## 最终复核

再次刷新远端引用并逐仓确认：

- 工作树是否干净；
- 是否仍有未推送提交或落后 upstream；
- 最终分支与提交 SHA；
- 验证、提交、拉取和推送结果；
- 无法处理的精确原因。
- 共享侧边栏布局的发布版本、已应用版本、项目置顶/排序和共同任务置顶结果。

最终按项目和仓库报告 `已是最新 / 已拉取 / 已提交并推送 / 阻塞`，同时报告两端项目并集和共享侧边栏布局是否完整。明确说明只能检查当前设备可访问的工作树；一台设备无法发现另一台离线设备尚未提交到 Git 的本地文件，项目并集和布局依赖两端各自在开始与交接时推送最新映射。
