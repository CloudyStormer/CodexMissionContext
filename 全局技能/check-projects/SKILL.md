# 检查项目

把本技能作为 A、B 两台设备的项目协作入口。项目共享范围采用并集：除明确排除项外，A 有的项目 B 也要有，B 有的项目 A 也要有；不通过删除获得一致。

## 判断运行模式

- **项目提交模式**：用户以命令方式发送“检查提交”“检查项目”“项目检查”或“项目提交”，或者明确要求检查所有项目是否已提交推送。
- **开始同步模式**：用户单独发送“开始”或“开始同步”。先同步上下文，再核对两端项目并集、补齐本机缺失项目并拉取远端。
- **交接模式**：用户要求“交接”“晚间交班”“下班交接”或汇报今天完成、新增及对方待办。先执行项目提交模式，再写入并推送精准交接记录，最后通知另一端。

这些模式只由用户主动触发，不创建定时任务，不在后台轮询。只按项目检查，不枚举、复制或同步临时任务、聊天和原始对话。

## 定位协作仓库

`CodexMissionContext` 固定位置：

- macOS：`~/Desktop/DEV/Life/CodexSpace/CodexMissionContext`
- Windows：`D:\.aaProject-Bruce\CodexMissionContext`

识别 `.device-id` 后读取：

1. `同步清单/项目清单.md`
2. `同步清单/增量对齐规则.md`
3. `设备/A/项目映射.md`
4. `设备/B/项目映射.md`
5. 当前设备的已应用清单版本

上下文仓库干净时先运行 `脚本/同步上下文.sh 开始`。若它已有修改，不要 reset 或覆盖；先 `fetch` 获取远端事实，把该仓库留到最后处理。

## 维护项目并集

“公共项目”指 A、B 可同步项目的并集，而不是交集。

1. 使用当前 Codex 的项目列表读取能力获取本机实际项目；若能力不可用，使用当前设备映射，并把覆盖范围标记为“部分”。
2. 将本机新增项目写入当前设备映射，并登记到 `同步清单/项目清单.md`。读取项目根目录及其中全部 Git remote，记录可供另一设备取得内容的克隆地址。
3. 拉取另一设备已推送的项目映射和并集清单。对本机缺失的并集项目：
   - 先验证名称、目标目录和 Git 来源；
   - macOS 放在 `~/Desktop/DEV/Life/CodexSpace/` 下；
   - Windows 放在 `D:\.aaProject-Bruce\` 下，禁止在 C 盘创建共同项目；
   - 克隆项目的每个组成仓库，验证默认分支、remote、HEAD 和工作树；
   - 使用正式 Codex 项目管理能力把真实项目根目录加入项目列表；
   - 回读本地 `projectId` 并写入当前设备映射。
4. 某项目缺少路径、Git 来源、权限或项目管理能力时，登记阻塞并继续其他项目；不创建空壳、不猜测仓库、不把同名 Skill 目录冒充项目。
5. 完成后更新已应用版本。只有并集中的全部项目在本机真实存在并完成映射时，才标记“完整应用”。

永久排除 `AI学习` 及其子目录，除非用户以后明确点名解除；没有本地 Git 路径的账号级云项目只报告，不克隆。不得删除、归档、重命名或隐藏任何现有项目。

## 发现项目中的全部仓库

不要把一个项目等同于一个仓库。项目根目录本身以及其下的独立 Git 工作树都要检查；例如 `lottery` 必须覆盖前端和后端两个仓库。

把已解析出的项目根目录交给只读盘点脚本：

```bash
bash scripts/inspect-project-repos.sh --fetch "/项目根目录一" "/项目根目录二"
```

脚本只发现仓库、刷新远端引用并输出状态，不会修改工作树、创建提交或推送。

先处理业务仓库，最后处理 `CodexMissionContext`。嵌套仓库先处理更深层的仓库，再处理父仓库。

## 远端优先的正规提交流程

对每个仓库先读取适用的 `AGENTS.md`，再执行：

1. 检查当前分支、upstream、remote、merge/rebase 状态和冲突。
2. 运行 `git fetch --all --prune`，先取得远端最新状态。
3. 检查工作树、暂存区、未跟踪文件、`git diff` 和 `git diff --cached`。
4. 工作树干净时先用 fast-forward 或非交互式 rebase 取得远端最新提交。
5. 工作树有修改且远端也前进时，先完整审查本地改动，再创建带时间标识的命名 stash（包含已跟踪和未跟踪改动）；拉取远端后用 `stash apply` 恢复。恢复冲突时保留 stash 和现场并阻塞；只有恢复内容已经成功提交后才删除该 stash。
6. 检查 `.env`、`auth.json`、令牌、密码、Cookie、SSH 私钥、数据库、session、缓存、异常大文件和明显生成垃圾。疑似敏感或误入内容时不提交。
7. 运行仓库已有且与改动相称的验证。验证失败时不推送，并保留完整错误。
8. 暂存全部确认安全的项目改动，按实际内容编写描述性提交信息；互不相关的内容拆成独立提交。
9. 再次 fetch；如远端出现新提交，安全 rebase。发生冲突立即中止 rebase，并保留本地提交。
10. 推送当前分支。push 遇到远端竞态时，重新 fetch、rebase 后最多重试一次。

“项目提交”授权处理检查范围内已有的普通项目改动，不限于当前对话产生的文件；无需为每个普通提交重复确认。但这不授权删除项目、改写历史、泄露凭证、绕过失败验证或掩盖冲突。

upstream 缺失时，只有 remote 和目标分支唯一明确才使用 `git push -u`；否则阻塞。禁止 force push、`reset --hard`、`clean`、删除项目或切换到不明分支。一个仓库阻塞时继续检查其他独立仓库。

## 处理上下文与交接

`CodexMissionContext` 最后处理。更新并集清单、设备映射、项目稳定事实及长期任务记录后运行：

```bash
./脚本/检查仓库.sh
./脚本/同步上下文.sh 结束 "检查项目：项目同步与交接"
```

交接记录使用中文精准压缩，至少包括：

- 当天处理过的项目和各仓库最终提交；
- 新增项目、克隆地址、项目组成和本地映射；
- 已完成的工作与验证结果；
- 另一设备需要拉取、安装、补建或继续的事项；
- 冲突、权限、网络、缺少 remote 等阻塞；
- 下一位同事可以直接执行的精确步骤。

上下文推送成功后，使用可用的 Codex 任务通信能力向另一设备的“ 双设备同步维护 ”任务发送简短交接通知。只有工具确认送达时才声称已通知；不可达时说明原因，并以远端上下文仓库作为待对方下次“开始同步”时读取的权威交接。

## 最终复核

再次刷新远端引用并逐仓确认：

- 工作树是否干净；
- 是否仍有未推送提交或落后 upstream；
- 最终分支与提交 SHA；
- 验证、提交、拉取和推送结果；
- 无法处理的精确原因。

最终按项目和仓库报告 `已是最新 / 已拉取 / 已提交并推送 / 阻塞`，同时报告两端项目并集是否完整。明确说明只能检查当前设备可访问的工作树；一台设备无法发现另一台离线设备尚未提交到 Git 的本地文件，项目并集依赖两端各自在开始与交接时推送最新映射。
