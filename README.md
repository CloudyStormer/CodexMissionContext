# CodexMissionContext

这是 A、B 两台设备共同使用的 Codex 持久化工作记忆仓库。

它解决五件事：

1. 每个需要长期续接的项目都有可持续更新的项目上下文。
2. 同步范围内所有侧边栏任务都采用两端并集，在另一端对应项目建立可见镜像，并写入可直接续接的精简语义上下文；需要长期维护的任务另有独立记录。
3. 两台设备在任务开始前拉取、结束后提交并推送最新记录。
4. 个人自制 Skill 通过同一个私有 Git 仓库同步。
5. 用户发送四字口令“开始同步”时，以同一运行 ID 尝试让 A、B 各自走查本机全部共同项目、全部 Git 仓库和全部同步范围任务；代码先拉取并安全对齐远端，再审查、验证、提交和推送安全的本地成果；任务补齐可见镜像并发送精简语义交接，最后核对两端侧边栏顺序和置顶。

## 核心原则

> Git 同步项目实体和持久化上下文；Codex 任务镜像同步可见任务与完整语义；原始会话数据库和本地运行状态留在本机。

这里的“完整语义”不是全量复制：无论项目大小，只同步经过整理的精准压缩总结，确保另一台设备能继续工作，同时避免搬运原始对话、整份项目内容和重复信息。

设备 A、B 只是本地映射标识，没有主次关系。用户会在两台设备之间交替工作；任一设备都必须先取得最新上下文，再继续、更新并推送。除明确排除项外，两端共同项目按项目列表并集计算：任一端新增的项目都要登记 Git 来源并补齐到另一端。

Windows 设备上的双设备共同项目统一存放在 `D:\.aaProject-Bruce\`，不得放到 C 盘。

本仓库记录：

- 项目目标、仓库地址、分支和当前提交。
- 用户要求、已确认结论、关键决定及原因。
- 已完成事项、修改文件、命令、测试结果和失败经验。
- 未解决问题、风险、精确下一步和交接指令。
- 个人 Skill 的完整文件。

本仓库禁止记录：

- `auth.json`、访问令牌、API Key、密码、Cookie、SSH 私钥。
- Codex 本地数据库、原始 session 目录、缓存和浏览器登录态。
- 无意义的完整聊天转录。任务记录必须保留完整语义，但要压缩重复表达。
- 项目本身已经由独立 Git 仓库管理的代码副本。

共享侧边栏布局只记录逻辑项目/任务 ID、从上到下的顺序、置顶状态和版本。允许只读解析本机相关状态以获得准确顺序，但绝不复制或提交 Codex 原始全局状态，也不直接写本地数据库；另一端只通过正式 API 或用户可见界面创建任务镜像并应用布局。原始消息不逐字复制，镜像任务使用精准压缩的可交接上下文。

## 每次任务的同步流程

### 开始任务

```bash
./脚本/同步上下文.sh 开始
```

然后依次读取：

1. `项目上下文/项目索引.md`
2. 对应项目的 `项目概览.md`
3. 对应项目最近的任务记录

### 结束任务

1. 当前任务属于同步范围时，更新逻辑任务映射与精简交接；只有需要长期维护时才使用模板新增或更新独立任务记录。
2. 只有稳定项目事实发生变化时，才更新对应项目的 `项目概览.md`。
3. 运行检查：

```bash
./脚本/检查仓库.sh
```

4. 提交并推送：

```bash
./脚本/同步上下文.sh 结束 "项目名：任务简述"
```

脚本只有在远端同步、检查和推送都成功时，才会报告完成。出现冲突或网络错误时必须停止并明确报告。

为防止“统一”演变成跨设备误删，自动同步脚本会拒绝本地或远端的删除、重命名；这类变更必须停止并人工核对。

## 主动项目同步与提交

`check-projects` 是第三个个人 Skill，支持：

- “开始”：读取两台设备已推送的项目映射，以并集为目标补齐本机缺失项目和仓库。
- 四字口令“开始同步”：生成唯一运行 ID；若另一设备维护任务可连接，只唤醒一次且禁止反向派发。A、B 各自刷新项目与任务并集，对本机全部共同项目仓库先 fetch/拉取远端，再审查、验证、提交和推送安全的本地普通改动；随后补齐缺失任务镜像、发送精简交接、对齐共享顺序与置顶，最后合并同一运行 ID 的两端报告。
- “检查提交”“检查项目”“项目检查”或“项目提交”：先取得远端状态，再遍历当前项目列表下的全部 Git 仓库；安全改动经验证后分别提交、对齐并推送。
- “交接”或晚间交班：完成项目提交，记录当天工作、新增项目和对方待办，推送后尝试通知另一端。

该功能只由用户主动触发，不建立定时任务，也不替代普通任务结束时只处理本任务改动的规则。“开始同步”会把共同项目全部可见任务取并集，在另一端建立同名可见镜像并发送完整但精简的交接语义；它不会复制原始聊天全文，也不会自动继续未获授权的业务遗留需求。检查范围限于各设备实际可访问的工作树和任务接口；另一台离线设备尚未提交的本地文件或未发布任务不可见。只有同一运行 ID 的两端成功报告均已取得，且代码、项目、任务镜像、语义交接与共享布局都验证成功，才可声称两端全部同步。

“开始同步”与“项目提交”使用同一正规提交流程。先完成全部可达仓库的远端取得阶段，再进入本地上传阶段；远端前进且本地有改动时使用可恢复的保护 stash 对齐并恢复，随后审查、验证、提交、再次 fetch/rebase、push，并验证本地与 upstream 一致。冲突、验证失败、凭证、敏感内容或业务歧义必须保留现场并报告，不能为了声称全部同步而盲目上传。

## 每日项目同步

`daily-project-sync` 只处理普通每日交班：按项目汇总当天任务，并轻量拉取、推送已经确认的代码成果，不逐文件复盘业务差异。它不处理四字口令“开始同步”；该口令始终由 `check-projects` 执行完整同步。

## 第二台设备接入

1. 把本仓库克隆到对应平台的固定位置。

macOS：

```bash
git clone git@github.com:CloudyStormer/CodexMissionContext.git ~/Desktop/DEV/Life/CodexSpace/CodexMissionContext
```

Windows PowerShell：

```powershell
git clone git@github.com:CloudyStormer/CodexMissionContext.git 'D:\.aaProject-Bruce\CodexMissionContext'
```

2. 在 Codex2 中打开克隆目录并启动一个任务，哪怕只发送“开始”。
3. 根目录 `AGENTS.md` 会自动进入 Codex 上下文，并直接执行设备 B 首次接入；不需要再粘贴任何说明。

设备标识 A、B 仅用于区分本地 `projectId`、`threadId` 和路径，不表示主设备或备用设备。

设备接入后必须先执行“只增不减”的项目与任务清单对齐。清单外项目和同步范围任务都进入两端并集；任务在对应项目中建立带精简交接语义的镜像，绝不通过删除获得表面一致。

在 Windows 设备上接入时，仓库固定使用 `D:\.aaProject-Bruce\CodexMissionContext`；其他共同项目也必须位于 `D:\.aaProject-Bruce\` 下。

注意：`git clone` 本身只下载文件，不会主动唤醒 Codex。必须在 Codex2 中打开该目录并启动一次任务；从那一刻起，无需额外解释。

仓库新增个人 Skill 后，另一台设备拉取最新提交并再次运行 `脚本/安装到本机.sh A|B`，随后重启 Codex 或新建任务，即可发现新 Skill。
